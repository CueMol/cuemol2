CueMol 2.3.15 (build 530)

This release opens CueMol3 up: a feature can now live in one directory and be
switched on or off from **Settings > Plugins**, instead of being wired into a
dozen tables across the app. Two new things arrive on that mechanism -- an **AI
agent chat panel** that builds a scene from a written instruction, and a **PyM
Console**, a partly PyMOL-compatible command line whose parser and Tab
completion are ported from PyMOL itself. Both are off by default.

On the rendering side, `dsurface` and `dsurf2` are merged into one renderer that
lets you pick the mesh algorithm, direct surfaces finally answer clicks and
hover, and a surface of sixteen million vertices no longer costs gigabytes of
colour. Cameras move out of the scene tree into a Camera pane of their own, in a
new View activity view, and their order is saved with the scene. A long-standing
defect is fixed underneath all of this: a named selection evaluated outside the
draw path -- from a script, a panel button, or a PDB write -- used to come back
silently empty.

Two changes will be visible without being asked for: the **MD trajectory GUI is
now a plugin and is off by default**, and **scenes saved with `dsurface` are now
drawn with the distance-field algorithm**. Both are covered under known
incompatibilities below.

CueMol2 (the UXP app) has no GUI changes of its own; it picks up the shared core
work -- the surface merge, the named-selection fix, the empty-selection guards in
zoom and center, and the measurement additions.

---

## Plugins

**A feature can now be one directory.** Adding one used to mean editing several
closed tables -- command ids, the menu template and its IPC channels, the toolbar
list, the activity-view and bottom-tab unions, the dialog provider list, the
worker service map -- and removing it meant touching the same number again, with
nothing in the app saying whether it could be turned off at all. A plugin now
declares what it contributes in one manifest and is switched from a single
setting. Seven contribution points are covered: commands, menu items, toolbar
buttons, an activity view with its side panes, bottom tabs, dialogs and worker
services.

**Settings > Plugins** lists them with a description and a switch. Choices are
remembered per plugin, and a plugin you have never touched follows its own
default -- so a default that changes later still reaches you.

Six plugins ship built in. *Get PDB* and *Sequence* are always on: they were made
plugins to keep them in one place, not to be removed. The *Component Catalog*
(an internal UI catalogue), the *AI agent*, *MD trajectory* and the *PyM Console*
are off by default.

## The AI agent chat panel (off by default)

Write what you want -- "load 1CRN and show it as a cartoon" -- and the model calls
the same services the GUI calls, in order, streaming its progress back into the
panel. Twenty tools cover loading, selection, renderers, colouring, scene
settings, interaction analysis, distance / angle / dihedral measurement and image
output.

- **One instruction is one undo step.** A single Cmd+Z takes the whole thing back.
- **Scene settings are reachable too** -- background colour, ambient occlusion,
  anti-aliasing and CMYK proofing are scene node properties, so the agent reaches
  them through the same generic property tools rather than one tool each.
- **OpenAI and Anthropic both work.** The model is configured as
  `provider:model`.
- **API keys go to the OS keychain**, not into a settings file.
- **Enter inserts a newline; Cmd/Ctrl+Enter sends** -- the other way round from
  the usual default, because the thing you lose by guessing wrong (a half-written
  prompt) is the one you cannot get back. Settings can swap the two.
- Sent prompts come back with the up and down arrows, shell style.

## PyM Console (off by default)

A bottom tab with a PyMOL-compatible command line, for people whose fingers
already know `fetch 1crn` and `bg_color white`. Full compatibility is not the
goal; running what you already know is.

**The parser is ported from PyMOL, not reinvented** -- line splitting, argument
parsing, the call preparation and the command abbreviation rules, down to the
error wording. The Tab completion is ported the same way, including its quirks:
Tab replaces the whole line and leaves the caret at the end, pressing it again
lists the same candidates rather than cycling, a command word is never completed
to itself while an exact argument match is accepted, and unknown entries fall back
to globbing filenames. Candidates print into the transcript, as they do in PyMOL.

Commands: loading and objects (`load` `fetch` `delete` `set_name` `cd` `pwd` `ls`
`enable` `disable` `get_names`), view (`zoom` `center` `reset` `turn` `move`
`view` `refresh`), settings (`set` `get` `unset` `bg_color`), output and history
(`png` `undo` `redo` `quit` `help`), selections (`select` `indicate` `deselect`
`count_atoms` `get_chains`), representations (`show` `hide` `as` `color`),
measurement (`distance` `angle` `dihedral`) and maps (`isomesh` `isosurface`
`isolevel`).

- **A selection expression is translated, not passed through.** The two languages
  agree on operator precedence but differ in their lexis -- a lone `+` is a union
  while a `+` inside a word is a list separator, a lone `-` is a difference while
  one inside a word is a range. `within` / `near_to` / `beyond` expand into
  CueMol's `expand` / `around`.
- **Anything without a faithful equivalent is refused by name, with a reason,**
  rather than quietly selecting different atoms. `neighbor` and `extend` are
  called out specially: CueMol's parser accepts them but has no implementation, so
  passing them through would return an empty selection and no error.
- **`show` / `hide` do not touch renderers you made in the GUI.** Each object and
  representation gets one renderer named `pym:<rep>` whose selection is widened by
  `show` and narrowed by `hide`; the prefix is the boundary.
- **One submit is one undo step**, with the same commit rule as the agent panel.

## Surfaces

**`dsurf2` is merged into `dsurface`, and you choose the algorithm.** The two were
the same renderer with the same properties, differing only in how the mesh was
built and whether the GPU path existed -- and the new-renderer list offered both
with nothing to tell you which to pick. There is now one `dsurface` with a
**Surface algorithm** setting, and the GPU path is available to all of them:

| Algorithm | Surface types |
|---|---|
| EDTSurf (voxel + distance transform) | vdw / sas / ses |
| Distance field + marching cubes (**default**) | vdw / sas / ses |
| MeshMS (analytic SES) -- **new** | ses only |

MeshMS meshes the analytic surface directly instead of walking a grid, which
makes it dramatically faster at high detail: on a 8829-atom structure at detail 32
it returns 1.7 million vertices in 2.6 seconds, where the distance field takes 17
seconds for 950 thousand. It needs a build with MeshMS enabled and only does SES,
so vdw / sas, a build without it, and a failed generation fall back to the
distance field and say why in the log.

**Detail now means the same thing in all three.** The three builders take
different quantities (a voxel size, a grid spacing, a target edge length), so the
value was recalibrated against EDTSurf: at the default detail of 6, all three land
within 4% of the same vertex count. The Detail choices are now
`1, 2, 4, 8, 16, 24, 32` -- 24 was added because the step from 16 to 32 costs more
than three times as much.

**A large surface no longer takes the process down.** The allocator Electron links
against dies on a *single* allocation over about 2 GB, so both builders are capped
by vertex count: MeshMS predicts its vertex count from the atom count and solves
for the finest mesh size that fits, with a hard ceiling that falls back to the
distance field; the distance field binary-searches for its spacing from the
molecule alone -- the previous approach of coarsening from the requested value
could make a *higher* detail come out coarser.

**Colour is no longer the biggest thing a mesh carries.** Mesh vertex colours were
an array of scriptable colour pointers at 72 bytes each, and potential or
multigradient colouring allocated a fresh 256-byte gradient object per vertex --
about 350 bytes of colour per vertex. Vertices now carry a 16-byte record indexing
a shared palette, whatever the colouring method: at 16 million vertices that is
about 256 MB instead of about 5.6 GB. **Exported files are unchanged** -- POV-Ray,
LuxRender, Metasequoia and umbreon output keeps the same colour table ordering and
gradient registrations.

**Direct surfaces answer the pointer.** They were not in the hit test at all, so a
click or a hover over one did nothing -- even though the answer was already there,
each mesh vertex carrying the id of the atom it belongs to. The hover chip, the
click label and the hover highlight all work on `dsurface` now, highlighting the
patch belonging to that atom. Picking applies to the **fill** draw mode; wireframe
and dots keep one name for the whole mesh and stay out of it. Rectangle and lasso
selection still ignore surfaces.

**The translucency threshold for picking moved from 0.5 to 0.6, inclusive.** A
surface at 0.6 opacity used to pick itself although you could still see through
it. Exactly 0.6 is now click-through and only something more opaque is picked.
This is a shared constant, so it applies to every renderer.

Also fixed: a potential crash where a mesh vertex with no owning atom was passed
to the selection node unchecked (the guard was testing an unsigned value for
negativity). Such vertices are drawn in the default colour.

## The 3D view

**The hover highlight is visible on a dark background.** Its outline is drawn in
two tones -- the inner line over the element's own colour, the outer line over the
background -- and the outer one was always dark, so on a black background with a
line renderer such as `simple` there was nothing to see. The outer tone is now
picked from the background's relative luminance: white on a dark background, the
previous dark line on a light one. The threshold is where white and the dark tone
give the same contrast, so neither side of it is the weak one, and it is a hard
switch rather than an interpolation -- a blended middle tone would be mid grey,
which is the worst value against a mid grey background. Luminance rather than HSB
brightness, so that a deep blue background is treated as dark. No new setting.

## Cameras

**Named cameras have a pane of their own.** They were a synthetic branch of the
scene tree, although a camera is a list of viewpoints rather than part of the
object hierarchy, and most of the operations were only in a right-click menu. A
new **View** activity view holds the **Camera pane** above the **View pane**;
Explorer keeps Scene and Color.

- Six toolbar buttons: **New / Save / Save with show-hide / Apply / Apply with
  show-hide / Delete** -- the context menu is no longer the only way.
- **Rows can be dragged to reorder**, and the order is saved in the scene file as
  the order of the camera elements. Dropping below the last row moves to the end.
  `__current` is listed as before but pinned at the top and not reorderable.
- **Creating a camera with an existing name overwrites it without asking**, as the
  UXP app does.
- Everything else is unchanged: F2 or the menu to rename, Delete to remove,
  double-click to apply with show/hide, copy and paste, camera file load / reload
  / save / save as, and editing or clearing the visibility flags.
- The camera branch is gone from the scene tree, and the dead *Properties* item is
  gone from the camera context menu (a camera has no uid, so it never resolved).

Two fixes found while building the pane landed in the shared kit, so they apply
everywhere: **a tooltip no longer opens when its target takes focus** (closing a
dialog returned focus to the button that opened it, and a tooltip appeared with
the mouse nowhere near), and **dragging a list row no longer drags selected text
along with it**.

## Selections and measurement (shared core)

**A named selection now resolves wherever it is evaluated.** A name defined by the
console's `select`, or by *Save as...* in the Selection Builder, is stored per
scene and resolved lazily -- and it was reading the style context current at that
moment. Drawing pushes the scene, so renderers were fine, but everything else --
scripts, worker services, a button in a panel, writing a PDB file -- ran outside it
and **silently matched nothing**. A compiled selection now keeps the scope it was
compiled in. As a consequence, **a named selection can refer to another named
selection**.

**Zoom and center on an empty selection no longer wreck the viewpoint.** An empty
bounding box is stored inverted, so it went into the calculation as-is and sent
the view to the origin with zoom and slab pinned at their minimum. Zero atoms now
leaves the view alone and reports that nothing matched -- in the console and from
the GUI's Zoom and Center buttons alike. A zero-sized box is widened to at least
4 A per axis about its centre, so a single atom or a collinear set no longer
divides by zero in the aspect calculation.

**Angles and dihedrals can be defined by selection.** The interaction element has
carried three modes since it was written -- atom ids, coordinates and selection --
and every drawing path already read a selection as the centroid of the matching
atoms, but only distance exposed it. Angle and dihedral now do too, and an
appended element whose selection matches nothing is rejected at that point instead
of being silently skipped on every redraw.

The scene-scoped style set that holds named selections was called `user`, which is
the name of the *global* scope where your own stylesheet is loaded at startup; two
different things had the same name. It is now `style_N`, as the UXP app proposes.

## Smaller changes in CueMol3

- **Confirming a Japanese IME conversion with Enter no longer submits.** Every
  Enter handler on a text input got the same check -- thirteen of them, including
  dialogs that predate this release.
- **Text is one step larger throughout the UI.** Labels went from 11 to 12 px,
  body text and list rows from 12 to 13 px, and so on; the relative order of the
  roles is unchanged, so the hierarchy is the same and everything is simply a
  size bigger. The three console surfaces -- the Output tab, the Rendering
  window's log and the PyM Console -- share a new console text role at 14 px,
  measured against VS Code's debug console.
- **The viewport's tool palette folds away.** A small cap at its top collapses it
  to a pill and back; *View > Tool palette* (`Cmd/Ctrl+Shift+P`) does the same, and
  the state is remembered.
- **Files can open into a new scene.** Object files always merged into the active
  scene. Two independent settings under *Settings > General > Files* now choose
  per entry point: **Drag and drop opens into** and **File manager opens into**
  (Finder / Explorer, the command line, and a second instance). Both default to
  the current scene, so nothing changes unless you opt in. *File > Open* and
  *Open Recent* always use the current scene, `.qsc` is never affected, "new
  scene" reuses an empty active scene rather than stranding it, and files opened
  together share one scene. Cancelling the options dialog no longer leaves an
  empty tab behind.
- **Point density for surface generation now defaults to 2 /A** instead of 1,
  which was inherited from the UXP number box initialising to its minimum and was
  too coarse to leave alone.
- **Loading a map from the console gives it a map renderer.** The common default
  was `simple` regardless of what the object was, and object creation does not
  check renderer compatibility, so a density map got a molecule line renderer and
  no contour.
- Fixed duplicated preset rows in the new-renderer list, caused by the global
  style being fetched twice.

## Known incompatibilities and limitations

- **The MD trajectory GUI is off by default.** *File > Open MD Trajectory...* and
  the Trajectory bottom tab are now the `mdtools` plugin, and only an explicit
  choice is remembered -- so everyone who has never touched the setting gets it
  off. Turn it on in **Settings > Plugins**. It is marked experimental there. A
  `Trajectory` already in a scene still renders and still loads from `.qsc`
  regardless; only the GUI is gated. Disabling the plugin while playback is
  running unmounts the tab and stops it.
- **Scenes saved with `dsurface` are now drawn with the distance field.** The
  algorithm setting was not written to the file because it did not exist, so it
  comes back at the new default. The mesh looks different and `detail` responds
  differently. Scenes saved with `dsurf2` resolve to `dsurface` with the distance
  field, which is what they had. The unimplemented `msms` value was removed.
- **Camera order is not preserved by older UXP builds.** Re-saving such a scene
  there returns the cameras to name order, since the UXP app has no notion of
  their order.
- **The AI agent works on one scene** -- the active one when the turn starts.
  Asking for a new scene still loads into the current one. A manual edit made
  while a turn is running is absorbed into the agent's undo step. The panel is
  reachable only from its activity view, not from a menu or command. The
  conversation itself lasts only for the session. Switching provider in the middle
  of a conversation is untested.
- **PyM Console measurements are one label per command**, treating each selection
  as its centroid; PyMOL's exhaustive pairing is deliberately not ported (its
  dihedral has no distance cutoff, so four hundred-atom selections would mean tens
  of millions of labels). Measurement is within one molecule. `isomesh`'s `buffer`
  and `carve` cannot be set independently, since one range serves both; passing
  both warns. `zoom`, `center` and carving act on one molecule -- the one the
  expression names, or the first one with a warning. `@script.pml` and raw Python
  are refused by name. `volume` and `isodot` are not implemented. Still to come:
  `save`, `label`, `spectrum`, `set_color`, the animation commands, `align` /
  `super`, and a wider PyMOL setting-name alias table.
- **On macOS, plugin rows are briefly absent from the native menu at startup**,
  since the native menu is built before the renderer reports its contributions.
- **The larger text is app-wide**, while control heights are still fixed in
  pixels; if something now looks cramped, please report it.
- The hover highlight on line renderers still draws a single outline with no fill,
  because the mask does not survive the blur; the earlier limits are unchanged --
  no highlight for symmetry copies, for renderers below the picking opacity
  threshold, or in stereo.
